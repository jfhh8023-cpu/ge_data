# REQ-060 第1轮：需求基线与数据来源

日期：2026-09-15。阶段：文档设计，只读探索，未获编码批准。

## 输入与需求基线

用户更正：交付率 = 已交付工时 / 总工时；已交付工时是每个人提交的所属周工时，标准每天8小时、周一至周五40小时，扣除节假日，按实际工作日计算；覆盖研发与AI产品经理。

- R1-D01：分子是提交工时，不乘任务交付进度，不按提交次数重复累计。
- R1-D02：分母是人员在所选周的应工作工时，不能使用已填写工时作分母。
- R1-D03：两类填报表继续独立存储，部门总量按原始记录只计一次。
- R1-D04：需求行 `delivery_progress` 与新交付率不是同一个量；旧指标替换边界待确认。

## 只读探索证据

- `frontend/src/utils/progress.js`：现行 `weightedProgress` 是工时加权任务进度，不是本次定义。
- `backend/src/routes/stats.js`：`records` 已合并两种来源，`productManagerRecords` 是产品专用副视图，不可二次相加。
- `backend/src/routes/fill.js`：提交时替换同人同任务旧记录；草稿保存在填报链接，不是正式工时行。
- `backend/src/models/WorkRecord.js` 与 `ProductManagerWorkRecord.js`：同有 hours、delivery_progress；表间ID不能假定全局唯一。
- 只读 GET `http://127.0.0.1:5176/api/stats?year=2026&quarter=Q3`：code=0，7个周任务、131条总记录（含2条产品记录）、12名当前非离职人员、10名有记录人员、总工时2328h。仅保存汇总，不归档姓名、填报令牌或webhook。

## 用例 v1

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| R1-T01 | 无假期周，提交32h | 32/40=80% |

| R1-T08 | “综合进度”改名/替换与需求行进度 | 需明确替换层级，禁止直接改写delivery_progress |
