# 四轮测试反哺需求机制

版本：v1.0  
发布日期：2026-09-12  
适用范围：跨页面、跨模块、涉及存储、统计、权限或外部通知的需求

## 1. 机制目标

把模糊需求先转换成可验收的产品契约，再用测试用例主动寻找遗漏和冲突，连续四轮收敛后才允许编码。该机制的产物必须能被另一位开发者、测试人员或其他 AI 独立复核，不依赖原聊天上下文。

## 2. 铁律流程

```text
原始需求
  ↓
第1轮：需求基线 → 开发测试计划 → 测试用例
  ↓ 用例反哺
第2轮：修订需求 → 修订计划 → 测试用例
  ↓ 用例反哺
第3轮：修订需求 → 修订计划 → 测试用例
  ↓ 用例反哺
第4轮：冻结需求 → 冻结计划 → 冻结用例
  ↓ 用户明确确认
开发 → 单元/API/浏览器/集成测试 → 发布评审
```

任何一轮出现关键歧义、数据迁移风险、权限绕过、统计口径不确定或无法验证的链路，都必须停留在文档阶段，并列入“待用户确认”或“阻塞项”。

## 3. 每轮必备产物

| 产物 | 必须回答的问题 |
| --- | --- |
| 需求文档 | 谁在什么页面、对什么数据、以什么规则完成什么目标？历史数据和异常情况如何处理？ |
| 开发测试计划 | 改哪些模块、接口、表、组件和统计逻辑？按什么顺序开发？如何回滚？ |
| 测试用例 | 正常、空值、零值、边界、冲突、权限、历史数据、导入导出和失败重试是否可验证？ |
| 反哺记录 | 上一轮哪些用例暴露了需求遗漏、歧义、错误假设或不可测条件？本轮怎么修正？ |

每个测试用例使用稳定编号，例如 `R1-F-001`（第1轮功能用例）、`R2-D-003`（第2轮数据用例）、`R4-E-002`（第4轮端到端用例）。后续轮次必须直接引用编号，不得只写“已覆盖”。

## 4. 四轮关注重点

### 第1轮：建立基线

- 把原始语言拆成角色、页面、字段、动作、数据来源、存储、统计和权限。
- 画出数据流：录入 → 保存 → API → 数据库 → 周期统计 → 报表/导出。
- 标出与现有行为冲突的地方，并给出待确认项。

### 第2轮：验证交互和字段

- 用例覆盖每个新增字段的默认值、必填、可选项、错误提示、粘贴解析和编辑行为。
- 检查所有页面和组件是否使用统一数据源，不允许局部硬编码。
- 反查响应式布局、页签默认项、空状态、零值和历史记录。

### 第3轮：验证数据和统计

- 验证存储隔离、历史兼容、双写/迁移边界、事务、幂等和回滚。
- 用最小数据集手算总数、工时、百分比、去重键和跨角色合计。
- 检查图表、卡片、明细、导出和 API 的同一筛选条件是否得到同一结果。

### 第4轮：冻结和发布门控

- 执行跨页面端到端矩阵，覆盖不同权限、不同屏幕、浏览器缩放、网络失败和并发操作。
- 清理未决项；仍未决的事项必须由用户明确选择，不能靠实现猜测。
- 在冻结文档中写明不做什么、历史数据如何保留、上线如何回滚。
- 用户确认冻结版三份文档后，才可创建代码任务或修改业务代码。

## 5. 质量门

- 没有需求编号：不开发。
- 没有上一轮用例引用：不进入下一轮。
- 关键统计口径未确认：不写入代码。
- 用例不能证明数据库未被错误修改：不通过。
- 任一高风险用例为 BLOCKER/FAIL：不冻结。
- 用户未明确确认冻结文档：不编码、不迁移、不推送、不发布。

## 6. 复制模板

```markdown
# [需求名称] 第N轮

## 本轮输入
- 上一轮需求文档：
- 上一轮开发测试计划：
- 上一轮测试用例：

## 本轮发现
| 来源用例编号 | 发现 | 影响 | 决策 |
| --- | --- | --- | --- |

## 需求修订
- [ ] 页面/字段：
- [ ] 数据/存储：
- [ ] 统计/导出：
- [ ] 权限/错误：

## 下一轮门禁
- 未决问题：
- 新增用例编号：
- 允许进入下一轮的条件：
```
