# 自动任务子通知与值班规则定点生效优化需求

日期：2026-08-09
状态：已确认，本地开发与验证完成
环境边界：仅修改和验证本地开发环境；不得推送远端仓库，不得发布生产，不得改动生产数据。

## 1. 需求来源

用户要求在现有“设置 / 自动执行任务并通知”中完成两项优化：

1. 每一条“自动任务创建并通知”主规则可配置 N 条子通知。主通知真实执行成功后，子通知才被激活，并按各自时间、内容和 webhook 目标独立发送。
2. 自动值班通知在固定模式与轮换模式互相切换时，可选择从本周或下周的任意星期开始生效；生效日前继续使用旧规则，生效日及以后使用新规则。

## 2. 范围与非范围

### 2.1 本次范围

- 自动任务创建并通知规则的子通知持久化、增删改、启停、状态、倒计时和调度发送。
- 子通知按主规则现有 webhook 连接选择全部、一个或多个目标。
- 每周/每月两种子通知计划，精确到时分秒。
- 固定/轮换值班规则的生效周、生效星期选择。
- 历史、当前和未来值班解析统一按生效日期选择规则版本。
- 设置页对应弹窗、状态反馈、错误反馈和本地测试。

### 2.2 本次不做

- 不增加新的通知渠道。
- 不改变主任务原有的任务创建、主 webhook 通知或测试发送语义。
- 不为自动值班通知增加子通知；子通知入口仅属于“自动任务创建并通知”。
- 不推送代码、不制作生产包、不发布生产。

## 3. 子通知详细规则

### 3.1 入口与数量

- 在主规则“保存通知”操作区域下一行靠右增加“子通知”按钮。
- 主规则保存后才允许进入子通知配置；未保存规则给出明确提示。
- 一条主规则可新增 N 条子通知，每条可独立编辑、启用、停用和删除。

### 3.2 计划配置

- 计划类型二选一：
  - `每周星期`：周一至周日可单选或多选。
  - `年内每月日期`：1-31 日可单选或多选，循环适用于每一年。
- 每条子通知配置一个精确 `HH:mm:ss` 时间。
- 月份不存在所选日期时跳过该月，不向月末最后一天折算。例如选择 31 日时，2 月、4 月、6 月、9 月、11 月不发送。
- 子通知在每次主通知激活周期内只发送一次；选择多个星期或日期表示取激活后的第一个匹配时间。

### 3.3 内容与目标

- 每条子通知有独立通知内容，支持随时编辑。
- webhook 目标只能来自当前主规则已保存且有效的 webhook 连接。
- 支持选择：全部 webhook、指定一个、指定多个。
- webhook 连接使用稳定标识保存；修改连接名称或地址后，原子通知目标关系不因列表序号变化而错位。
- 子通知沿用主通知的接收人/@ 配置，不重复增加一套接收人配置。

### 3.4 激活门禁

- 只有同时满足以下条件，子通知才会被主通知激活：
  - 主规则已启用。
  - 主规则通知能力已启用。
  - 主规则由计划调度真实触发。
  - 主 webhook 通知发送成功。
  - 子通知自身已启用。
- 测试执行、测试发送 webhook、手动保存规则均不得激活子通知。
- 主任务跳过、主通知失败、仅执行规则不通知时，不激活子通知。
- 主规则被停用或切换为不通知模式时，尚未发送的子通知立即失活；重新启用主规则本身不会恢复旧激活周期，必须等待下一次主通知真实成功。
- 主通知每成功执行一次，生成一个新的激活轮次，并将当时已启用的子通知重新置为待发送。

### 3.5 状态与倒计时

- 每条子通知独立显示：
  - `待主任务触发`：尚未被主通知激活。
  - `待发送`：已激活，等待本轮第一个匹配时间。
  - `已发送`：本轮已经成功发送，等待下一次主通知重新激活。
  - `发送失败`：本轮发送失败，展示错误原因，等待下一次主通知重新激活。
  - `已停用`：子通知自身关闭。
- `待发送`状态显示独立秒级倒计时；其他状态显示对应说明。
- 服务重启后状态、激活轮次和发送结果必须保留，不能因重启重复武装或丢失。

### 3.6 幂等与失败

- 同一子通知在同一主通知激活轮次最多进入一次实际发送流程。
- 调度器使用数据库状态抢占，避免多次轮询造成重复发送。
- webhook 失败记录错误并标记本轮失败，不循环重发造成其他已成功 webhook 重复收到；下一次主通知成功后再重新激活。

## 4. 值班模式定点生效详细规则

### 4.1 生效时间选择

- 每周星期值班配置中，固定模式与轮换模式单选保留。
- 当模式发生变化时显示“生效时间”配置：
  - 生效周：`本周起` / `下周起`。
  - 生效星期：周一至周日任意一天。
- 默认值为“本周起 + 周一”，与现有立即按本周计算的行为兼容。
- 月度值班配置不增加模式切换或生效日期能力。

### 4.2 新旧规则拼接

- 生效日期 = 所选自然周的周一 + 所选星期偏移。
- 生效日期之前使用旧规则；生效日期当天及以后使用新规则。
- 示例：选择“下周起 + 周三”时，本周全部日期以及下周周一、周二使用旧规则；下周周三开始使用新规则。
- 固定转轮换、轮换转固定均遵循同一规则。
- 多次切换均保存为按日期排序的规则版本，不覆盖更早版本，历史查询和已发生排班保持可复现。

### 4.3 轮换锚点

- 轮换模式的新人员顺序从生效日期开始计数。
- 若生效日期属于轮换排班区间，生效日由勾选顺序第 1 人值班。
- 若生效日期不在轮换排班区间，例如排班到周五但选择周六生效，则下一个实际排班日由第 1 人开始。
- 之后只按实际纳入排班区间的日期推进顺序，不因周末或未排班日跳号。
- 原“不重复排、不漏排”和按勾选顺序轮换规则保持不变。

### 4.4 统一解析

以下位置必须使用同一个“按日期选择生效规则版本”结果：

- 每周值班概览。
- 单日值班配置弹窗回显。
- 最近一次通知预览与状态。
- 后续三周排期。
- 下次通知倒计时。
- 后端日期匹配、调度事件生成和实际 webhook 发送。

### 4.5 待生效提示

- 存在未来生效的模式切换时，配置弹窗显示最近一条待生效规则的模式和准确日期。
- 当前概览继续展示当前日期实际生效的模式，不提前把未来规则当作当前规则。
- 固定模式实际生效期间，当前周说明和“后续”按钮仍按既有规则隐藏；轮换模式实际生效后再显示。

## 5. 数据设计

### 5.1 子通知表

新增 `auto_task_child_notifications`，核心字段：

- `id`、`rule_id`。
- `enabled`。
- `schedule_type`、`week_days`、`month_days`、`execute_time`。
- `message`。
- `webhook_target_mode`、`webhook_ids`。
- `activation_token`、`activation_scheduled_at`、`activated_at`。
- `status`、`last_scheduled_at`、`last_sent_at`、`last_error`。
- `created_at`、`updated_at`。

删除主规则时同步删除其子通知。

### 5.2 webhook 稳定标识

主规则 `dingtalk_webhook` JSON 中的每个对象补充 `id`。旧数据缺少 ID 时按现有 URL 生成稳定标识；接口读取后保存可继续沿用该 ID。

### 5.3 值班版本

继续使用 `auto_task_rules.duty_config` JSON，不新增值班数据库列。新增：

```json
{
  "weekly_versions": [
    {
      "effective_date": "1900-01-01",
      "weekly_mode": "fixed",
      "weekly": {},
      "weekly_rotation": {}
    },
    {
      "effective_date": "2026-08-12",
      "weekly_mode": "rotation",
      "weekly": {},
      "weekly_rotation": {
        "start_date": "2026-08-12"
      }
    }
  ]
}
```

- 旧数据没有 `weekly_versions` 时继续按原 `weekly`、`weekly_mode`、`weekly_rotation` 工作。
- 第一次定点切换时自动创建旧规则基线版本和新规则生效版本。
- 同一生效日期再次保存时替换该日期版本，避免重复版本产生歧义。

## 6. API 改动

- `GET /api/settings/auto-tasks`：每条主规则返回 `child_notifications` 和各子通知 `next_run_at`。
- `POST /api/settings/auto-tasks/:id/child-notifications`：新增子通知。
- `PUT /api/settings/auto-tasks/:id/child-notifications/:childId`：编辑子通知。
- `PATCH /api/settings/auto-tasks/:id/child-notifications/:childId/status`：启停子通知。
- `DELETE /api/settings/auto-tasks/:id/child-notifications/:childId`：删除子通知。
- 以上接口沿用设置页自动任务编辑权限边界和现有错误响应风格。

## 7. 验收标准

### 7.1 子通知

1. 一条已保存主规则可创建、编辑、启停和删除多条子通知。
2. 周计划支持 1-7 多选，月计划支持 1-31 多选，时间精确到秒。
3. 可选择全部、单个或多个主规则 webhook，主 webhook 删除后子通知不能误发到其他连接。
4. 主规则未真实成功通知时，满足子通知时间也不发送。
5. 主通知成功后，已启用子通知变为待发送并出现独立倒计时。
6. 子通知在当前激活轮次发送一次后显示已发送，不在同一轮次重复发送。
7. 主规则关闭会使待发送子通知失活；仅重新开启不激活，下一次主通知成功后才重新待发送。
8. 测试执行和测试发送 webhook 不激活子通知。
9. 选择 31 日时，小月不产生无效日期，也不改在月末发送。

### 7.2 值班切换

1. 固定转轮换和轮换转固定都必须选择本周/下周和周一至周日。
2. 本周周一生效与原行为一致。
3. 下周周三生效时，当前周及下周一二保持旧人员，下周三开始显示新规则人员。
4. 轮换生效日从勾选顺序第 1 人开始；生效日在非排班日时，下一个排班日从第 1 人开始。
5. 多次切换后，过去日期、当前日期和后续三周均按对应版本显示。
6. 页面概览、预览、倒计时、API 下次执行和实际调度人员一致。
7. 旧 `duty_config` 无需人工迁移即可正常读取和保存。

## 8. 质量与安全门槛

- 后端对计划类型、日期范围、时间格式、内容、webhook 目标归属进行校验，前端输入不可绕过。
- 子通知只能访问其路径参数所属主规则，防止跨规则修改。
- webhook 地址不写入日志、提示历史或前端静态代码。
- 自动测试不得向真实生产 webhook 发送消息；使用本地模拟 webhook 或禁用测试规则。
- 完成后执行后端语法、前端构建、数据库/API、调度幂等、页面交互和视觉截图验证，并写入开发记录。

## 9. 子通知列表与前置状态交互优化（2026-08-09 补充）

### 9.1 列表与编辑分层

- “子通知”主弹窗只展示已经保存的子通知列表，不在列表中直接铺开全部编辑字段。
- 列表至少展示序号、计划与时间、通知内容、webhook 目标、通知状态、独立倒计时、启用状态和操作。
- 点击“新增子通知”打开独立新增弹窗；点击列表“编辑”打开同一编辑弹窗并回显保存内容。
- 新增内容在保存成功前不进入列表；编辑内容在保存成功前不覆盖列表中的已保存值。
- 保存成功后直接关闭编辑弹窗、刷新列表并显示“子通知保存成功”的非阻断式成功提示，不增加二次确认。
- 删除操作继续保留现有危险操作确认。

### 9.2 倒计时与前置条件

- 已保存子通知的列表行必须显示该子通知当前倒计时或对应生命周期说明。
- 编辑已保存子通知时，编辑弹窗也必须显示其当前状态和倒计时；新增未保存通知显示“保存后等待主任务触发”。
- 子通知列表弹窗和新增/编辑弹窗都显示以下真实前置状态：
  - 主任务是否启用，以及最近一次真实计划执行结果和时间。
  - 主通知是否开启，以及最近一次真实计划通知结果和时间。
  - 主通知下一次计划触发倒计时和准确时间。
- 最近执行情况取真实调度运行日志，不把“测试执行”或“测试发送 webhook”冒充为子通知激活前置条件。

### 9.3 入口位置

- “子通知”入口仍属于“自动任务创建并通知”的通知操作区。
- 入口与通知开关放在同一右侧操作列，位于其紧邻下一行，缩小垂直间距，避免与开关视觉脱节。

### 9.4 补充验收标准

1. 打开子通知主弹窗时只看到已保存通知列表，不直接出现编辑表单。
2. 新增和编辑均通过独立弹窗完成；保存一次即成功，不出现二次确认框。
3. 列表与编辑弹窗同时具备子通知倒计时和主任务/主通知真实执行状态。
4. 无真实调度日志时明确显示“等待首次执行/通知”，不能显示伪成功状态。
5. 子通知入口与通知开关视觉紧邻，且各断点布局无重叠或横向溢出。

## 10. 待生效排班预览与全日期页签编辑（2026-08-09 补充）

### 10.1 概览操作区

- 每周值班规则存在未来生效版本时，在“批量编辑/引用”左侧显示“待生效排班”。
- 点击“待生效排班”后，从未来版本的准确生效日期开始，展示生效日所在自然周及后续两个自然周，共三个自然周的每日排班。
- 生效日以前但处于首个自然周内的日期保留位置并明确标记“生效前”，不能错误显示为新规则排班。
- 在“批量编辑/引用”左侧增加“编辑”入口；原单个星期/日期点击编辑和批量编辑/引用功能继续保留。

### 10.2 全星期与全日期编辑

- “编辑”复用现有单日值班配置弹窗和字段，不另建第二套业务表单。
- 周规则在弹窗顶部展示周一至周日 7 个标准页签，名称为“星期一”至“星期日”；页签可切换并完整回显当前版本全部星期配置。
- 月规则在弹窗顶部展示 1-31 共 31 个标准页签，名称仅显示日期数字；全部页签保持单行、完整可选，不使用按钮组样式。
- 切换页签时先保留当前页未提交编辑，再回显目标页内容；最终点击一次“保存通知”统一保存本次编辑内容。
- 每个页签继续具备现有人员、通知时间、发送策略、开始/结束文案、引用配置、预览和名句搭配能力。

### 10.3 待生效规则重新编辑

- 单日或全页签弹窗检测到未来生效版本时，在“待生效”提示右侧显示“重新编辑”。
- 点击后载入该未来版本的模式、全部星期内容、轮换区间、轮换人员顺序和生效时间，并自动进入全星期页签编辑。
- 重新保存时替换原未来版本；若调整生效日期，删除原日期版本后写入新日期版本，不能同时留下两条含义相同的待生效规则。
- 重新编辑期间允许调整固定/轮换模式、人员、轮换顺序、每日通知内容及本周/下周与星期组合。
- 未点击保存前不修改规则数据；退出弹窗不应改变当前或待生效排班。

### 10.4 验收标准

1. 有未来版本时显示“待生效排班”，无未来版本时不显示。
2. 待生效预览固定为三个自然周，日期、自然周编号、人员、时间和配置状态与按日期解析结果一致。
3. 周编辑顶部恰好 7 个页签，月编辑顶部恰好 31 个页签；均为单行标准页签且无页面横向溢出。
4. 任意两个页签之间来回切换，未保存内容不丢失；保存后重新打开可完整回显。
5. “重新编辑”能载入原待生效版本，保存后未来版本数量不因同一调整重复增加。
6. 生效日前仍使用旧版本，生效日及以后使用重新编辑后的新版本。
7. 本轮仅修改本地开发环境，不提交、不推送、不发包、不发布，不改动生产数据。

## 12. 主通知触发缺失时的子通知兜底激活（2026-08-09 补充）

### 12.1 需求背景

- 正常情况下，主规则按计划真实执行且主 webhook 发送成功后，后端立即激活已启用的子通知，子通知进入独立倒计时。
- 若子通知是在本周期主通知成功后才新增，或历史执行检测记录缺失，子通知可能一直显示“待主任务触发”，与主通知已开启且下次执行倒计时正常的实际状态不一致。

### 12.2 判定优先级

1. 真实计划执行且主通知成功的正常激活逻辑优先级最高，继续按现有状态机执行。
2. 若本周期存在主任务真实执行记录：
   - `status = success` 且 `notify_status = success` 时，可作为主任务和主通知已经触发的佐证，并补激活尚未进入生命周期的子通知。
   - 执行中、跳过、执行失败、通知失败或本轮未通知是明确结果，不得被倒计时兜底规则覆盖。
3. 若本周期没有检测到可用的真实执行记录，只有同时满足以下条件才默认主任务已经触发：
   - 主规则已启用；
   - 主通知已开启，且不是 `run_only`；
   - 主任务下次执行时间存在并处于正常倒计时；
   - 当前时间到下次执行时间严格小于 `6 × 24` 小时。
4. 恰好等于 6 天或大于 6 天不匹配；倒计时无效、已经过期、主规则停用或主通知关闭均不匹配。
5. 测试执行、主通知测试发送、子通知测试发送和普通保存记录均不得作为佐证。

### 12.3 补激活行为

- 兜底逻辑只处理 `enabled = true`、`status = inactive` 且没有 `activation_token` 的子通知。
- 已待发送、发送中、已发送或发送失败的子通知不得被兜底重复激活。
- 使用本周期最近一个应执行时间作为补激活时间；子通知自身仍遵守创建/修改时间、星期或日期、精确时分秒及“一轮只发送一次”约束。
- 补激活采用数据库条件更新和新的激活令牌，调度器每秒检查时不会重复生成激活轮次。
- 有历史成功记录时记录“历史成功记录佐证补激活”；无记录时记录“倒计时规则兜底补激活”，便于审计但不暴露 webhook。

### 12.4 界面提示

- 鼠标悬停在“子通知状态/倒计时”单元格时显示完整匹配规则 Tooltip。
- 提示必须说明：真实成功优先；缺少检测记录时才使用“主通知开启 + 有效倒计时 + 小于 6 天”兜底；明确失败/跳过不兜底；测试操作不参与。
- 正常真实激活的显示和倒计时逻辑保持不变；兜底补激活成功后同样显示“待发送”和真实子通知倒计时。
- 倒计时内容不得使用低对比灰色；待发送使用蓝色、已发送使用绿色、发送失败使用红色、未激活/等待使用琥珀色，文字和数字清晰可见且不改变列表尺寸。

### 12.5 验收标准

1. 本周期真实主任务和主通知成功，但子通知尚未激活时，可依据运行日志补为待发送。
2. 本周期没有真实运行日志，但主规则/通知开启且有效倒计时小于 6 天时，可补为待发送。
3. 本周期存在执行中、跳过、失败或通知失败记录时，不使用倒计时兜底。
4. 倒计时等于或超过 6 天、主规则停用、主通知关闭、`run_only` 均不补激活。
5. 同一子通知重复执行调度检查只补激活一次，不重复发送。
6. 红框所示状态/倒计时区域悬停可见完整规则，页面不新增横向溢出。
7. 列表和编辑弹窗的倒计时均按状态显示高对比颜色，不再显示为灰色。
8. 完成本地验证后，按“先推送、生产备份、`--skip-db` 发布、数据守恒验证”的顺序发布生产。
